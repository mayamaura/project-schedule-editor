データモデル

Git で差分・マージしやすいことを最優先に設計する。ファイル形式がそのまま UX（競合の起きやすさ）を決めるため、早期に確定したい。

1. エンティティ

エンティティ主な属性
Projectid, name, parentId, order, status, assignee, tags[], color, note
Eventid, projectId, name, start, end, type, color, style?, note
Milestoneid, projectId, name, date, type, style?, note
Dependencyid, from{kind,id}, to{kind,id}, type(FS/SS/FF/SF), lagDays
Type（種別マスタ）id, name, color, eventStyle, milestoneStyle
Template（標準日程）id, name, defaultAnchor, dayMode, adjust, events, milestones, dependencies（起点（0）からの相対オフセット: ヶ月・日）
Viewid, name, shared, visibleProjectIds, expanded, zoom, dependencyFilter, columns
Calendarweekend設定, holidays[], 稼働日
MetaschemaVersion, appVersion
  • ID: UUID（または短い乱数ID）。名前や順序をキーにしない（名前変更・並べ替えで競合させない）。
  • 日付: ISO 8601 の日付のみ（2026-11-07）。時刻・タイムゾーンを持たない。終了日は「含む」（決定 K5）。例: start: 2026-12-01, end: 2026-12-15 は 12/1〜12/15 の15日間。期間の日数は end − start + 1、表示上のバーの右端は終了日の翌日の0時（日単位の幅）とする。
  • 順序: 配列インデックスでなく fractional index（文字列）にすると、並べ替えが1要素の変更で済み競合しにくい。

2.1 calendar.json（カレンダー設定。F-603）

{
  "holidays": { "2026-12-29": "年末休業" },   // 会社の休日・追加の休み（日付 → 名称）
  "japaneseHolidays": true,                  // 日本の祝日（振替休日・国民の休日を含む）を休みにする
  "weekend": [0, 6],                         // 毎週の休みの曜日（0=日曜 … 6=土曜）
  "workdays": { "2027-01-02": "休日出勤" }    // 特別稼働日（休みに勝つ）
}
  • ファイルが無ければ既定（日本の祝日あり・土日休み・追加なし）。出力規則は他と同じ。日程の自動保存の対象外で、calendar:save で個別に保存する。他の人の更新とはファイル単位の 3 版で合わせる（architecture 15.4）。
  • 日本の祝日はデータに持たず、アプリが計算する（1980〜2099 年）。判定は「特別稼働日 → 休みの曜日 → 会社の休日 → 日本の祝日」。

方式比較

方式利点欠点
A. 1プロジェクト1ファイル（推奨）別プロジェクトを別々の人が編集しても競合しない。履歴がプロジェクト単位で追えるファイル数が増える（数千まで許容）
B. 全体を1つの JSON実装が単純誰かが編集するたび競合しやすい。非推奨
C. 1イベント1ファイル最も競合しにくいファイルが膨大、読み込みコスト大
D. SQLite高速バイナリで差分・マージ不可。不可
整形ルール: キー順固定・インデント2・末尾改行・配列は ID 順。アプリが書き出す形式を一意に固定して、無意味な差分を出さない。親子は parentId を子側に持たせる（親ファイルに子リストを持たない）。

4. 競合の単位とマージ方針

  • 通常の Git 3-way マージ（テキスト）でほぼ解決できるよう、1フィールド=1行で出力。
  • それでも衝突した場合、アプリが JSON を 3 つ（base/ours/theirs）読み、エンティティ・フィールド単位で比較して業務語で提示（Git連携・UX）。
  • 将来案: カスタム merge driver でアプリ外 Git クライアントでも自動マージ（優先度低）。

4.5 日程変更の検出と表示

「いつ・誰が・どの日程をどう変えたか」をアプリ上で表示する機能の仕組み。行単位の git diff テキストは解析しない（整形や行位置に依存して壊れやすいため）。

検出方式

  1. git diff --name-status <旧> <新> で変更のあったファイルだけを特定（追加 A / 変更 M / 削除 D）。
  2. 各ファイルを git show <版>:<パス> で両版取得し、JSON としてパース・スキーマ検証。
  3. ドメイン層の純関数 diffSchedule(old, new): Change[] が、ID をキーにエンティティ・フィールド単位で比較。
  4. 名称変更や並べ替えでも ID が同じなら「同一物の変更」として追跡する。

変更の種類（Change）

種類例表示
追加 / 削除イベント・マイルストーン・プロジェクト・依存の追加/削除緑 / 打消し線
日付変更マイルストーン 3/1→3/15（+14日）、イベント開始・終了の変更（期間の伸縮も算出）旧位置に影、新位置に実体、矢印と日数差
移動（親子）親プロジェクトの付け替え旧親→新親を文で表示
属性変更名称・状態・担当・種別・色変更前→変更後
依存の変更依存の追加/削除、タイプ・ラグの変更線を緑/赤で強調
波及変更により依存違反が新たに発生した（警告）警告アイコンと一覧

表示場面

  • 保存時: 現在の編集内容と最新コミットの差分を要約（例:「新製品A: リリース 3/1 → 3/15（+14日）」）。
  • 共有時: 取り込む他者の変更を、取り込み前に一覧表示。
  • 履歴: 各コミットの変更要約。コミットを選ぶとタイムライン上で差分表示。
  • 2版比較: 任意の2つの版（コミット/日付/タグ）をタイムライン上で重ねて比較。
  • 競合解決: base / 自分 / 相手の3版を同じ diff 関数で比較し、項目単位の選択に使う。
  • 編集中: 直前の保存版からの変更箇所をバー上に印（任意）で表示。

フィルタ・集計

期間・プロジェクト・変更種類・作者で絞り込み、「日程が後ろ倒しになった項目」を一覧（変動日数の降順）する。

同じ diffSchedule を、保存・共有・履歴・比較・競合解決のすべてで再利用する。純TypeScript のため単体テストを必須とする。性能は変更ファイルのみ読むため、リポジトリ全体が大きくても影響しない。

5. スキーマ進化

  • schemaVersion を保持。起動時に古ければマイグレーションし、「データ形式を更新しました」を1コミットとして記録。
  • 新しいバージョンのデータを古いアプリが開いた場合は読み取り専用で警告。

6. AI 提案（ChangeSet）

実装（2026-11-08。src/domain/ai/changeset.ts）: 下の例のとおり op と ID で表す。実装した op は addProject / updateProject / deleteProject / addEvent / updateEvent / deleteEvent / addMilestone / updateMilestone / deleteMilestone / addDependency / updateDependency / deleteDependency。更新は変更するフィールドだけを持つ（eventId・milestoneId・projectId・dependencyId で指す）。追加には tempId を付けられ、同じ提案内の後続の変更から参照できる（承認時に新しい ID に置き換える）。依存の種類は kind（FS/SS/FF/SF）。1 つの提案は 1〜200 件の変更。承認されたものは、1 つの batch コマンド（Undo 1 単位）として適用する。

AI が返す日程変更案の形式。ドメインのコマンド列であり、UI の編集操作と同じ経路で適用される。Git には保存しない（ローカルのアプリデータ領域、F-710）。承認・適用された結果だけが通常のデータ変更として保存・commit される。

{
  "id": "cs-20261107-001",
  "createdAt": "2026-11-07T10:00:00+09:00",
  "summary": "設計フェーズを2週間延長し、後続の試作を後ろ倒し",
  "rationale": "レビュー日程が設計完了に依存しているため",
  "changes": [
    { "op": "updateEvent", "projectId": "3f9a1c", "eventId": "e1", "end": "2026-12-29" },
    { "op": "updateEvent", "projectId": "3f9a1c", "eventId": "e2", "start": "2027-01-19", "end": "2027-04-14" },
    { "op": "updateMilestone", "projectId": "3f9a1c", "milestoneId": "m1", "date": "2026-12-30" }

}
  • op は domain のコマンド名（add/update/delete × Event/Milestone/Project/Dependency など）。未知の op・存在しない ID・不正な日付は zod/検証で拒否。
  • 適用前に diffSchedule でプレビュー、適用後は validateSchedule で新たな不整合が出ていないか確認して併せて表示する。
  • 問題一覧（ValidationIssue）: { rule, severity, target:{kind,id}, message }。ルールベース（F-704）と AI の指摘（F-705、rule:"ai"）を同じ形式で扱う。

8. 標準日程（Template）

実装: src/domain/template.ts（architecture 15）。よく使う日程のひな形。起点（0ヶ月 / 0週）からの相対オフセット（ヶ月・日。負=起点より前、正=後）で保持し、展開時に起点の日付を与えて実日付に変換する。起点はマイルストーンである必要はなく、標準日程上の基準となる点（0）である（F-801〜F-808）。チーム共有のため Git の templates/<id>.json（1標準日程1ファイル、他と同じ出力規則）に保存する。

{
  "id": "tpl-release-std",
  "name": "標準リリース日程",
  "defaultAnchor": "m-release",     // 展開時に「マイルストーン起点」を選んだときの既定（任意）。起点(0)自体は暗黙
  "dayMode": "calendar",            // 日の数え方: "calendar"（暦日）| "working"（稼働日）
  "adjust": "none",                 // 非稼働日の補正: "none" | "earlier" | "later"
  "events": {
    "t1": { "name": "設計",   "type": "phase",
            "start": { "months": -4 },                "end": { "months": -2, "days": -15 } },
    "t2": { "name": "試作",   "type": "phase",
            "start": { "months": -2, "days": -10 },   "end": { "months": -1 } },
    "t3": { "name": "保守",   "type": "phase",
            "start": { "months": 1 },                 "end": { "months": 6 } }
  },
  "milestones": {
    "m-review":  { "name": "設計レビュー",   "type": "review",  "date": { "months": -2, "days": -14 } },
    "m-release": { "name": "リリース",       "type": "release", "date": {} },
    "m-post":    { "name": "納品後レビュー", "type": "review",  "date": { "months": 1 } }
  },
  "dependencies": {
    "d1": { "from": { "kind": "event", "id": "t1" }, "to": { "kind": "event", "id": "t2" }, "type": "FS", "lagDays": 4 }
  }
}
  • オフセットは { "months": 整数, "days": 整数 }（どちらも省略可、省略は 0。符号は負=前、正=後）。画面では 日/週/ヶ月 の単位で入力でき、週は日（×7）に換算して保存する。
  • 起点より前（負）の項目も後（正）の項目も、同じ標準日程に定義できる。
  • ヶ月と日を併用するときは同じ向き（両方が負、または両方が正）にする（読み込み時に検査する）。
  • 標準日程は日程（Schedule）とは別のファイル群で、自動保存の対象外。他の人の更新とは、ファイル単位の 3 版で合わせる（双方が同じ標準日程を変えたら自分の版を残す。architecture 15.1）。

展開の計算

  1. 展開時に、起点（0）の実日付 D0 を決める（F-802）。(a) マイルストーン起点: 標準日程内の任意のマイルストーン M（既定は defaultAnchor）を選び、その実日付 DM を指定する → D0 = DM に M のオフセットを逆向きに適用した日付（M のオフセットが 0 なら D0 = DM）。(b) 起点の日付: D0 を直接指定する。
  2. 各項目の実日付 = D0 にその項目のオフセットを適用した日付。適用順は「ヶ月を暦月で加減算 → 日を加減算」。ヶ月の加減算で存在しない日付になる場合は月末に丸める（3/31 −1ヶ月 = 2/28、閏年は 2/29。決定 F7）。dayMode が working のとき、日の部分は稼働日数で数える。
  3. 非稼働日に当たった場合は adjust に従って前倒し/後ろ倒し（既定は補正なし）。
  4. 結果は新規 ID を持つコマンド列（addProject / addEvent / addMilestone / addDependency）として生成し、diffSchedule でプレビュー、承認後に1コマンドとして適用する（Undo 1単位）。AI 提案（ChangeSet）と同じ経路。
  5. 展開後のプロジェクトは標準日程への参照を持たない（独立）。
月の加減算は暦月で行うため加法的でない（「3/31 の1ヶ月前」の1ヶ月後は 2/28 → 3/28 で元に戻らない）。(a) のようにマイルストーンを起点に選ぶと、D0 の逆算で月末付近に数日のずれが出る場合がある。ずれはプレビューで確認・調整できるようにする。単体テスト（月末・閏年・年またぎ・稼働日）は必須。

9. 書き込みと復旧

  • 全ファイルの書き込みは一時ファイル → fsync → rename（原子的置換）。部分的に書かれたファイルを作らない。
  • 自動保存はこれらのファイルを直接更新する（Git の作業ツリーの変更 = 履歴に未記録の変更）。アプリ専用の領域 .autosave/（running・pending.json・flow.json）は Git 管理外（共有される .gitignore ではなく、リポジトリ内の除外設定 .git/info/exclude へアプリが登録する。実装済み）。
  • 起動時にスキーマ検証と参照整合の検証を行い、不整合は修復案とともに提示する（データを黙って削除しない）。詳細は architecture 8。

11. ドメイン層の実装仕様（Phase 1）

実装: src/domain/（純 TypeScript。テスト: tests/domain/）。要件: F-206, F-208, F-301, F-305, F-509, NF-004〜006。以下のうち「仮定」は、ユーザーの決定事項ではなく Phase 1 での設計判断（変更があれば /spec-change）。

項目仕様
モジュールdate（日付計算）／model（型と zod スキーマ）／order（fractional index）／serialize（整形出力・読み込み・スキーマ版管理）／validate（整合性チェック）／commands＋history（コマンド適用・Undo/Redo）／diff（diffSchedule）／sample（性能検証用データ生成）
日付（K5 決定を反映）文字列 YYYY-MM-DD のみ（年は 0001〜9999）。内部は「1970-01-01 からの通算日数」の整数演算で、Date 型・タイムゾーンを使わない。期間の日数は end − start + 1。週は月曜始まり。月の加減算は暦月で、存在しない日は月末に丸める（F7）
ID（仮定）不透明な文字列（[A-Za-z0-9_-]{1,64}）。生成は domain の外（UUID 等）で行い、コマンドに含める（テストが決定的になる）。全プロジェクト・イベント・マイルストーン・依存で一意（種類をまたいで重複不可）
集約（Schedule）{ schemaVersion, projects, dependencies, types }。projects は ID をキーとし、各プロジェクトが events と milestones を ID キーのオブジェクトで持つ。不変データとして扱い、更新は変更した部分だけ新しいオブジェクトにする（構造共有）
依存の判定式（仮定）終了日を含むため、FS: 後続.開始 ≥ 先行.終了 + 1 + ラグ、SS: 後続.開始 ≥ 先行.開始 + ラグ、FF: 後続.終了 ≥ 先行.終了 + ラグ、SF: 後続.終了 ≥ 先行.開始 + ラグ。マイルストーンは開始＝終了＝日付。違反は警告のみ（A2。自動連動しない）。ラグは負の値も可
コマンド（F-206）add / update / delete × Project・Event・Milestone・Dependency、moveProject（親・並び順）、batch（複数コマンドを1つの Undo 単位に）。適用前に検証し、失敗なら理由コード付きのエラーを返して状態を変えない。ドラッグなどの連続操作は確定時に1コマンド
拒否する操作（F-208, F-301）存在しない ID／ID の重複／不正な日付／終了＜開始／プロジェクトの循環（自分の子孫を親にする）／自己依存・重複依存・依存の循環／存在しない端点への依存。依存違反は拒否せず警告（編集の自由を優先）
削除の連鎖（仮定）プロジェクトの削除は子孫のプロジェクト、それらのイベント・マイルストーン、それらを端点とする依存も削除。イベント・マイルストーンの削除も、それを端点とする依存を削除。Undo で全て復元
Undo/Redo（仮定）変更前のスナップショット（構造共有のため 25,000 イベントでも軽量）を履歴に積む。深さの既定は 1,000。新しいコマンドで Redo 履歴は破棄
整合性チェック（F-704 の基礎）validateSchedule(schedule) → ValidationIssue[]（{ rule, severity, target, message }）。ルール: date-invalid / id-mismatch（キーと内容の id の不一致）/ end-before-start / dependency-violation（警告）/ dependency-cycle / dangling-reference / parent-cycle / duplicate-id / child-outside-parent（警告）。ファイルを外部で編集された場合に備え、読み込み後に実行する
差分（F-509）diffSchedule(old, new) → Change[]。種類: プロジェクトの追加・削除・改名・親/順序の変更・属性変更、イベント/マイルストーンの追加・削除・日付変更（変動日数つき）・属性変更、依存の追加・削除・変更。ID で対応付けるため、改名・並べ替え・プロジェクト間の移動でも同一物として追跡する。出力は決定的な順序（保存・テストのため）
整形出力（NF-005）キー昇順（再帰）、インデント2、LF、末尾改行、値に undefined を出さない。serializeSchedule は { パス: 文字列 } を返す（schedule.json / types.json / projects/<id>.json / dependencies/<id>.json）。往復して同一になる（テストで保証）。ファイル I/O は main 層（原子的書き込み）が担当
読み込みエラー（F-501, F-211）parseSchedule は、構造が壊れているとき全ての問題をパス付きで1回で返す（JSON の構文エラーと、別のファイルのスキーマ違反を同時に）。データを黙って捨てない。例外: 古い版は、全ファイルが読めないと移行できないため、構文エラーだけを返す。意味の不整合（終了＜開始など）は、読み込めたうえで issues として返す
スキーマ版（NF-006）schedule.json の schemaVersion（現在 1）。新しい版は読み取り専用で開く（tooNew）。古い版は migrate（版ごとの純関数の連鎖）で上げる
並び順（order）fractional index（文字列。orderBetween(a, b) が a と b の間の文字列を返す）。並べ替えは1要素の変更で済む

11.1 実測: 実際の Git でのマージ（Git 2.55、tests/main/gitMerge.test.ts）

整形出力した JSON を、実際の Git で2人が別々に編集して取り込む（merge）実験の結果。「競合しにくい」は条件付きで成り立つ。

2人の編集Git の自動マージ
別々のプロジェクト（別ファイル）／別々の依存の追加／別IDのプロジェクトの追加／並べ替えと別プロジェクトの編集○ 競合しない
同じプロジェクトの離れたイベントの編集○ 競合しない
同じプロジェクトへの追加（既存イベントを挟んだ別々の隙間）○ 競合しない
同じイベントの、離れたフィールド（例: 名称と種別）の編集○ 競合しない
同じイベントの、隣り合うフィールド（例: 名称と終了日）の編集✕ 競合する。キーが昇順（end, name, start, type）のため行が隣り合う。意味の上では衝突していない（別のフィールド）
同じプロジェクトの末尾へ、新しいイベントを追加どうし✕ 競合する。直前の行にカンマが付くため
同じイベントの同じフィールドを別の値に変更✕ 競合する（本来の競合。アプリの競合解決 UI で解決）
設計への含意（Phase 4 の S4-5 に反映）: Git の行単位の競合のうち、意味の上では衝突していないもの（上の「隣り合うフィールド」「末尾への追加」）が起きる。競合解決は、Git の競合マーカーを読むのではなく、git show :1:/:2:/:3: で取れる base / 自分 / 相手の3版を JSON として読み、エンティティ・フィールド単位で比較して、重ならない変更は自動で取り込み、同じ項目の同じフィールドが食い違うときだけ利用者に選んでもらう（F-506）。これで、利用者が見る競合は「本当の衝突」だけになる。ドメイン層に mergeSchedules(base, ours, theirs)（純関数）を置く想定。書式の変更（1フィールド1行をやめて隣接を避ける等）は、差分の読みやすさを損なうため採らない。
