データモデル

Git で差分・マージしやすいことを最優先に設計する。ファイル形式がそのまま UX（競合の起きやすさ）を決めるため、早期に確定したい。

1. エンティティ

エンティティ主な属性
Projectid, name, parentId, order, status, assignee, tags[], color, note
Eventid, projectId, name, start, end, type, color, style?, note
Milestoneid, projectId, name, date, type, style?, note
Dependencyid, from{kind,id}, to{kind,id}, type(FS/SS/FF/SF), lagDays
Type（種別マスタ）id, name, color, eventStyle, milestoneStyle
Template（標準日程）id, name, defaultAnchor, dayMode, adjust, events, milestones, dependencies（基準からの相対オフセット: ヶ月・日）
Viewid, name, shared, visibleProjectIds, expanded, zoom, dependencyFilter, columns
Calendarweekend設定, holidays[], 稼働日
MetaschemaVersion, appVersion
  • ID: UUID（または短い乱数ID）。名前や順序をキーにしない（名前変更・並べ替えで競合させない）。
  • 日付: ISO 8601 の日付のみ（2026-11-07）。時刻・タイムゾーンを持たない。終了日は「含む」か「含まない」かを仕様で固定（提案: 含む）。
  • 順序: 配列インデックスでなく fractional index（文字列）にすると、並べ替えが1要素の変更で済み競合しにくい。

2. Git 上のファイル構成（案）

schedule-data/
├─ schedule.json            # schemaVersion、設定
├─ calendar.json
├─ types.json
├─ projects/
│   ├─ 3f9a….json           # 1プロジェクト = 1ファイル
│   └─ 7c21….json           #   (events, milestones を内包)
├─ dependencies/
│   └─ a81b….json           # 1依存 = 1ファイル（または projects 側に持たせる）
├─ views/                   # 共有ビューのみ
│   └─ overview.json
├─ templates/               # 標準日程（チーム共有）
│   └─ tpl-release-std.json
└─ ai-prompts/              # AI への共有指示・観点
    └─ pt-release-risk.json

方式比較

方式利点欠点
A. 1プロジェクト1ファイル（推奨）別プロジェクトの同時編集は競合しない。履歴がプロジェクト単位で追えるファイル数が増える（数千まで許容）
B. 全体を1つの JSON実装が単純誰かが編集するたび競合しやすい。非推奨
C. 1イベント1ファイル最も競合しにくいファイルが膨大、読み込みコスト大
D. SQLite高速バイナリで差分・マージ不可。不可
整形ルール: キー順固定・インデント2・末尾改行・配列は ID 順。アプリが書き出す形式を一意に固定して、無意味な差分を出さない。親子は parentId を子側に持たせる（親ファイルに子リストを持たない）。

3. ファイル例

{
  "id": "3f9a1c",
  "name": "新製品A開発",
  "parentId": "root-01",
  "order": "a0",
  "status": "inProgress",
  "events": {
    "e1": { "name": "設計", "start": "2026-11-01", "end": "2026-12-15", "type": "phase" },
    "e2": { "name": "試作", "start": "2027-01-05", "end": "2027-03-31", "type": "phase" }
  },
  "milestones": {
    "m1": { "name": "設計レビュー", "date": "2026-12-16", "type": "review" }
  }
}

events / milestones は配列ではなく ID をキーにしたオブジェクトとする（キー順は ID 昇順で固定）。要素の追加・削除が他の行に波及せず、末尾カンマ起因の偽の競合が起きにくい。

3.5 形式の決定: JSON（確定）

項目決定
形式JSON。YAML は日付の型自動変換・出力の揺れ・パース差異のリスクがあるため不採用
出力規則キー昇順、インデント2、1フィールド1行、末尾改行、LF 固定（.gitattributes で eol=lf）
日付文字列 YYYY-MM-DD（型変換されない）
読み込みzod でスキーマ検証してから使用

4. 競合の単位とマージ方針

  • 通常の Git 3-way マージ（テキスト）でほぼ解決できるよう、1フィールド=1行で出力。
  • それでも衝突した場合、アプリが JSON を 3 つ（base/ours/theirs）読み、エンティティ・フィールド単位で比較して業務語で提示（Git連携・UX）。
  • 将来案: カスタム merge driver でアプリ外 Git クライアントでも自動マージ（優先度低）。

4.5 日程変更の検出と表示

「いつ・誰が・どの日程をどう変えたか」をアプリ上で表示する機能の仕組み。行単位の git diff テキストは解析しない（整形や行位置に依存して壊れやすいため）。

検出方式

  1. git diff --name-status <旧> <新> で変更のあったファイルだけを特定（追加 A / 変更 M / 削除 D）。
  2. 各ファイルを git show <版>:<パス> で両版取得し、JSON としてパース・スキーマ検証。
  3. ドメイン層の純関数 diffSchedule(old, new): Change[] が、ID をキーにエンティティ・フィールド単位で比較。
  4. 名称変更や並べ替えでも ID が同じなら「同一物の変更」として追跡する。

変更の種類（Change）

種類例表示
追加 / 削除イベント・マイルストーン・プロジェクト・依存の追加/削除緑 / 打消し線
日付変更マイルストーン 3/1→3/15（+14日）、イベント開始・終了の変更（期間の伸縮も算出）旧位置に影、新位置に実体、矢印と日数差
移動（親子）親プロジェクトの付け替え旧親→新親を文で表示
属性変更名称・状態・担当・種別・色変更前→変更後
依存の変更依存の追加/削除、タイプ・ラグの変更線を緑/赤で強調
波及変更により依存違反が新たに発生した（警告）警告アイコンと一覧

表示場面

  • 保存時: 現在の編集内容と最新コミットの差分を要約（例:「新製品A: リリース 3/1 → 3/15（+14日）」）。
  • 共有時: 取り込む他者の変更を、取り込み前に一覧表示。
  • 履歴: 各コミットの変更要約。コミットを選ぶとタイムライン上で差分表示。
  • 2版比較: 任意の2つの版（コミット/日付/タグ）をタイムライン上で重ねて比較。
  • 競合解決: base / 自分 / 相手の3版を同じ diff 関数で比較し、項目単位の選択に使う。
  • 編集中: 直前の保存版からの変更箇所をバー上に印（任意）で表示。

フィルタ・集計

期間・プロジェクト・変更種類・作者で絞り込み、「日程が後ろ倒しになった項目」を一覧（変動日数の降順）する。

同じ diffSchedule を、保存・共有・履歴・比較・競合解決のすべてで再利用する。純TypeScript のため単体テストを必須とする。性能は変更ファイルのみ読むため、リポジトリ全体が大きくても影響しない。

5. スキーマ進化

  • schemaVersion を保持。起動時に古ければマイグレーションし、「データ形式を更新しました」を1コミットとして記録。
  • 新しいバージョンのデータを古いアプリが開いた場合は読み取り専用で警告。

6. AI 提案（ChangeSet）

AI が返す日程変更案の形式。ドメインのコマンド列であり、UI の編集操作と同じ経路で適用される。Git には保存しない（ローカルのアプリデータ領域、F-710）。承認・適用された結果だけが通常のデータ変更として保存・commit される。

{
  "id": "cs-20261107-001",
  "createdAt": "2026-11-07T10:00:00+09:00",
  "summary": "設計フェーズを2週間延長し、後続の試作を後ろ倒し",
  "rationale": "レビュー日程が設計完了に依存しているため",
  "changes": [
    { "op": "updateEvent", "projectId": "3f9a1c", "eventId": "e1", "end": "2026-12-29" },
    { "op": "updateEvent", "projectId": "3f9a1c", "eventId": "e2", "start": "2027-01-19", "end": "2027-04-14" },
    { "op": "updateMilestone", "projectId": "3f9a1c", "milestoneId": "m1", "date": "2026-12-30" }
  ]
}
  • op は domain のコマンド名（add/update/delete × Event/Milestone/Project/Dependency など）。未知の op・存在しない ID・不正な日付は zod/検証で拒否。
  • 適用前に diffSchedule でプレビュー、適用後は validateSchedule で新たな不整合が出ていないか確認して併せて表示する。
  • 問題一覧（ValidationIssue）: { rule, severity, target:{kind,id}, message }。ルールベース（F-704）と AI の指摘（F-705、rule:"ai"）を同じ形式で扱う。

8. 標準日程（Template）

よく使う日程のひな形。基準マイルストーン（オフセット 0）からの相対オフセット（ヶ月・日。負=基準より前、正=後）で保持し、展開時に起点の日付を与えて実日付に変換する（F-801〜F-808）。チーム共有のため Git の templates/<id>.json（1標準日程1ファイル、他と同じ出力規則）に保存する。

{
  "id": "tpl-release-std",
  "name": "標準リリース日程",
  "defaultAnchor": "m-release",     // 基準マイルストーン（オフセット 0）。必須
  "dayMode": "calendar",            // 日の数え方: "calendar"（暦日）| "working"（稼働日）
  "adjust": "none",                 // 非稼働日の補正: "none" | "earlier" | "later"
  "events": {
    "t1": { "name": "設計",   "type": "phase",
            "start": { "months": -4 },                "end": { "months": -2, "days": -15 } },
    "t2": { "name": "試作",   "type": "phase",
            "start": { "months": -2, "days": -10 },   "end": { "months": -1 } },
    "t3": { "name": "保守",   "type": "phase",
            "start": { "months": 1 },                 "end": { "months": 6 } }
  },
  "milestones": {
    "m-review":  { "name": "設計レビュー",   "type": "review",  "date": { "months": -2, "days": -14 } },
    "m-release": { "name": "リリース",       "type": "release", "date": {} },
    "m-post":    { "name": "納品後レビュー", "type": "review",  "date": { "months": 1 } }
  },
  "dependencies": {
    "d1": { "from": { "kind": "event", "id": "t1" }, "to": { "kind": "event", "id": "t2" }, "type": "FS", "lagDays": 4 }
  }
}
  • オフセットは { "months": 整数, "days": 整数 }（どちらも省略可、省略は 0。符号は負=前、正=後）。画面では 日/週/ヶ月 の単位で入力でき、週は日（×7）に換算して保存する。
  • 起点より前（負）の項目も後（正）の項目も、同じ標準日程に定義できる。

展開の計算

  1. 展開時に起点を指定する（F-802）。(a) マイルストーン起点: 標準日程内の任意のマイルストーン M（既定は defaultAnchor）とその実日付 DM。(b) 開始日起点: 標準日程全体の開始日となる実日付 Ds のみ。
  2. まず基準マイルストーン（オフセット 0）の実日付 D0 を求める。(a) では D0 = DM に M のオフセットを逆向きに適用した日付（M が基準なら D0 = DM）。(b) では、最も早い項目の日付が Ds になるよう D0 を決める。
  3. 各項目の実日付 = D0 にその項目のオフセットを適用した日付。適用順は「ヶ月を暦月で加減算 → 日を加減算」。ヶ月の加減算で存在しない日付になる場合は月末に丸める（3/31 −1ヶ月 = 2/28、閏年は 2/29。月末の扱いは決定済み: F7）。dayMode が working のとき、日の部分は稼働日数で数える。
  4. 非稼働日に当たった場合は adjust に従って前倒し/後ろ倒し（既定は補正なし）。
  5. 結果は新規 ID を持つコマンド列（addProject / addEvent / addMilestone / addDependency）として生成し、diffSchedule でプレビュー、承認後に1コマンドとして適用する（Undo 1単位）。AI 提案（ChangeSet）と同じ経路。
  6. 展開後のプロジェクトは標準日程への参照を持たない（独立）。
月の加減算は暦月で行うため加法的でない（「3/31 の1ヶ月前」の1ヶ月後は 2/28 → 3/28 で元に戻らない）。起点に基準以外のマイルストーンを選ぶと、D0 の逆算で月末付近に数日のずれが出る場合がある。ずれはプレビューで確認・調整できるようにする。単体テスト（月末・閏年・年またぎ・稼働日）は必須。
属性の追加（予算・工数・進捗率など）、データ形式の希望を追記。
