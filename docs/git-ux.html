Git連携・UX

方針: Git の概念を隠し、業務の言葉に翻訳する。利用者に見せる操作は「履歴に残す」「共有する」「履歴」「戻す」（と作業版の操作）だけ。「保存」は自動保存（F-210）の意味に限り、履歴に残す操作には使わない（Windows の一般的な「保存」と紛らわしいため。2026-11-08 決定）。破壊的操作は提供しない。

1. 用語マッピング

画面上の言葉Git の操作
変更を履歴に残す（メモを添える）add + commit
共有する（正式版を直接編集しているとき）pull --no-rebase（取り込み）→ push
正式版の最新を取り込むfetch + merge
正式版（main）main ブランチ
作業版を作る / 作業版main の最新からの branch（内部名 work/日付-識別子、表示名は branch.<名>.description に保存）
正式版に反映する作業版へ main を merge（競合は作業版側で解決）→ main を作業版へ merge --no-ff → push
バックアップ作業版の push
作業版を整理する一覧から非表示（アーカイブ用の ref に移す。ブランチは強制削除しない）
履歴log
この版に戻す過去版の内容を新しいコミットとして適用（revert 相当。履歴は消さない）
競合merge conflict →「他の人の変更とぶつかっています」

2. 主要フロー

2.1 初回セットアップ（ウィザード）

  1. 「データの場所」: (a) 共有リポジトリURLから取得 / (b) 既存フォルダを開く / (c) 新規作成
  2. 名前とメールの設定（コミット作者用）
  3. Git の確認と認証: アプリが使う Git（利用者がインストールした外部の Git。見つからなければインストールを案内）を選び、ブラウザでサインイン（Git Credential Manager）。使えない場合は Device Flow / トークン。接続先ホストの設定（EMU の ghe.com 等）。
  4. 接続テスト → 完了

2.2 日常の編集

  1. 編集すると画面下に「履歴に未記録の変更: 3件」。変更した項目は一覧で日本語表示。変更は自動保存されており、アプリが落ちても失われない（F-210）。[履歴に残す] は「ここまでを記録する」操作（Windows の一般的な「保存」とは別物）。
  2. [履歴に残す] → 変更要約（自動生成）を確認、メモ（任意、既定は要約）→ commit。
  3. 作業版にいるときは、履歴に残すことを重ねて、まとまったら [正式版に反映する]（2.5）。正式版を直接編集しているときの [共有] は 取り込み＋送信。成功/競合/オフライン を平易な文言で通知。

起動時と一定間隔で fetch し、「他の人が更新しました（2件）→ 取り込む」を通知。未保存の編集中に自動マージはしない。

AI 提案を承認して適用した変更も、通常の編集と同じく「履歴に残す」を経て初めて commit される。AI が自動で保存・共有することはない（F-702, F-711）。

2.3 競合解決

実測（data-model 11.1）: Git の行単位のマージは、同じイベントの隣り合うフィールドの編集や、末尾への追加どうしで、意味の上では衝突していなくても競合する。そのため、競合は Git の競合マーカーで見せず、3版を項目・フィールド単位で比較し、重ならない変更は自動で取り込んで、同じ項目の同じフィールドが食い違うときだけ下の手順で選んでもらう。
  1. 「ぶつかった項目」を一覧（プロジェクト名＋項目名）。
  2. 各項目で「あなた: 3/15」「相手(山田, 11/6): 3/20」を並べて表示し、どちらか／手入力を選択。
    タイムライン上で両案を並べたプレビューも表示。
  3. 全項目解決で merge commit。途中でやめる場合は「やめる」で元の状態に完全復帰。

両者が同じプロジェクトを削除/編集した、親子付け替えが衝突した、など構造的な競合の扱いはデータモデルと併せて詳細設計が必要。

2.4 履歴・比較・復元

  • 履歴: 日時・作者・メモ・変更要約の一覧。選択でその時点のスケジュールを読み取り専用で表示。
  • 比較: 任意の2版をタイムライン上で差分表示（追加=緑、変更=旧位置の影+矢印、削除=打消し線）。
  • 復元: 「この版の日程を現在に反映」→ 通常の未保存変更として取り込み、確認後に保存。

2.5 作業版（自分だけで編集 → 正式版へ反映）

決定（2026-11-07）: 日程編集者は Git に詳しくない前提で、「自分用の作業版で、しばらく自分だけで編集・保存し、まとまったら正式版に反映する」流れを標準とする。用語（作業版 / 正式版 / 反映）は決定済み（G1）。

正式版   ──●────●────────────●────●──▶   （全員が見る版）
              \                  ↗ 反映
作業版         ●──●──●──●──●──┘        （自分だけ。保存を何度でも）

2.5.1 作業版を作る

  1. [作業版を作る] → 名前を入力（例:「11月改訂案」）。
  2. アプリが正式版の最新を自動で取得し、そこから作業版を作成。以後、その作業版で編集する。

2.5.2 今どこにいるかを常に表示

  • 画面上部に [正式版]（青の帯）または [作業版: 11月改訂案]（緑の帯）を常時表示。クリックで切替・作業版の一覧（名前・最終更新・正式版との差）。
  • 切替時に保存前の変更があれば、自動で退避し、元の版に戻ったときに復元する（確認メッセージで知らせる）。
  • 正式版にいるときは「作業版を作って編集しますか？」と控えめに案内（F-520 の直接編集は確認付きで可能）。

2.5.3 作業版での編集・保存

  • 編集・[履歴に残す]・履歴・戻すは、作業版の中で完結し、他の人には見えない。
  • [バックアップ]（任意）で作業版をリモートに送れる（PC 故障への備え。F-516）。

2.5.4 正式版に反映する（ウィザード）

  1. 最新の確認: 「正式版が更新されています（3件）。作業版に取り込みます」。
  2. ぶつかった項目の解決（あれば）: 2.3 の競合解決を作業版の中で行う。正式版には競合を持ち込まない。
  3. 確認: 正式版との差分（タイムライン上＋変更一覧）、新たな不整合（F-704）、反映するメモ。
  4. [反映する] → 正式版へ反映して共有。他の人が直前に更新していた場合は、自動で 1 からやり直し、「その間に更新がありました。もう一度確認します」と案内。
  5. 完了: 「反映しました」。作業版は「続ける / 整理する」を選択。

2.5.5 途中で落ちたら

反映や競合解決の途中で落ちても、再起動後に状態を検出して「続きから再開 / 最初からやり直し」を提示する（F-521）。編集中の変更自体は自動保存で残る（F-210/211）。

作業版の運用ルール（命名、整理の目安、複数人が同じ範囲を同時期に作業するときの注意など）を追記。

3. 安全策

方針内容
破壊的操作の不提供force push、reset --hard、履歴書き換え、ブランチ強制削除は UI に出さない
失敗時の復元マージ前に自動で退避タグ/参照を作成し、「元に戻す」で復帰可能
エラー文言Git の生エラーは「詳細を表示」に隔離。原因と次の行動を日本語で提示（認証失敗→トークン再設定、等）
データ検証取り込み後に全ファイルをスキーマ検証。壊れたデータは読み込み前に警告
Git と認証の診断Git のパス・版、認証、リモート接続、SSO 承認の状態を診断し、原因と対処を日本語で表示（F-523）。認証情報は平文でログ・設定に残さない
自動保存・復旧編集は約1秒ごとに自動保存。異常終了後の起動時に復元（F-210/211）。反映や競合解決の途中状態も再開可能（F-521）
反映の安全性反映前に「元に戻す」用の退避参照を作成。送信が拒否されたら自動で最新を取り込んでやり直す。強制送信は提供しない
上級者向け設定に「Git の詳細を表示」スイッチ（コマンドログ、リポジトリ場所を開く）
決定事項: リモートは GitHub、共同編集者は数人（編集は1人ずつ。共有は Git リモート経由の非同期）、運用は案B（作業版で編集 → 正式版 main へ反映）（2026-11-07 に案A から変更）。認証は Git Credential Manager のブラウザ認証（第一候補）、代替は GitHub Device Flow / PAT。Git は外部（システム）のものも同梱のものも使える（F-522）。アプリ外の Git クライアントで直接編集された場合にも念のため備え、読み込み時のスキーマ検証と出力規則の厳守（データモデル）で壊れたデータを防ぐ。
