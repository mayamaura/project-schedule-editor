Git連携・UX

方針: Git の概念を隠し、業務の言葉に翻訳する。利用者に見せる操作は「保存」「共有」「履歴」「戻す」だけ。破壊的操作は提供しない。

1. 用語マッピング

画面上の言葉Git の操作
変更を保存（メモを添える）add + commit
共有するpull --no-rebase（取り込み）→ push
最新を取り込むfetch + merge
履歴log
この版に戻す過去版の内容を新しいコミットとして適用（revert 相当。履歴は消さない）
案（シナリオ）branch
競合merge conflict →「他の人の変更とぶつかっています」

2. 主要フロー

2.1 初回セットアップ（ウィザード）

  1. 「データの場所」: (a) 共有リポジトリURLから取得 / (b) 既存フォルダを開く / (c) 新規作成
  2. 名前とメールの設定（コミット作者用）
  3. 認証（トークン貼り付け等。OS 資格情報ストアに保存）
  4. 接続テスト → 完了

2.2 日常の編集

  1. 編集すると画面下に「未保存の変更: 3件」。変更した項目は一覧で日本語表示。
  2. [保存] → 変更要約（自動生成）を確認、メモ（任意、既定は要約）→ commit。
  3. [共有] → 取り込み＋送信。成功/競合/オフライン を平易な文言で通知。

起動時と一定間隔で fetch し、「他の人が更新しました（2件）→ 取り込む」を通知。未保存の編集中に自動マージはしない。

2.3 競合解決

  1. 「ぶつかった項目」を一覧（プロジェクト名＋項目名）。
  2. 各項目で「あなた: 3/15」「相手(山田, 11/6): 3/20」を並べて表示し、どちらか／手入力を選択。
    タイムライン上で両案を並べたプレビューも表示。
  3. 全項目解決で merge commit。途中でやめる場合は「やめる」で元の状態に完全復帰。

両者が同じプロジェクトを削除/編集した、親子付け替えが衝突した、など構造的な競合の扱いはデータモデルと併せて詳細設計が必要。

2.4 履歴・比較・復元

  • 履歴: 日時・作者・メモ・変更要約の一覧。選択でその時点のスケジュールを読み取り専用で表示。
  • 比較: 任意の2版をタイムライン上で差分表示（追加=緑、変更=旧位置の影+矢印、削除=打消し線）。
  • 復元: 「この版の日程を現在に反映」→ 通常の未保存変更として取り込み、確認後に保存。

3. 安全策

方針内容
破壊的操作の不提供force push、reset --hard、履歴書き換え、ブランチ強制削除は UI に出さない
失敗時の復元マージ前に自動で退避タグ/参照を作成し、「元に戻す」で復帰可能
エラー文言Git の生エラーは「詳細を表示」に隔離。原因と次の行動を日本語で提示（認証失敗→トークン再設定、等）
データ検証取り込み後に全ファイルをスキーマ検証。壊れたデータは読み込み前に警告
上級者向け設定に「Git の詳細を表示」スイッチ（コマンドログ、リポジトリ場所を開く）
決定事項: リモートは GitHub、同時編集者は数人、運用は案A（main 単一ブランチ）。認証は GitHub Device Flow または PAT。Git 経由の共有が基本のため、アプリ外の Git クライアントで編集される場合も想定し、読み込み時のスキーマ検証と出力規則の厳守（データモデル）で壊れたデータを防ぐ。

4. 運用モデルの選択肢

案内容向き
A. 単一ブランチ(main)で全員が共有最もシンプル。競合は項目単位UIで解決小〜中規模チーム（推奨）
B. 案（ブランチ）で検討→採用「何ケース」かの日程シナリオを比較。採用時にマージ日程調整が多い運用
C. 編集権限/承認フローPR/レビューを経て反映厳格な統制が必要な場合
想定する同時編集者数、リモートの種類（GitHub / GitLab / 社内サーバ / 共有フォルダのみ）、運用ルールを追記。
