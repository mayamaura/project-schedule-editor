開発ルール（AI との協働ハーネス）

設計・実装・テストを AI（Claude Code）と進めるためのルールと、それを機械的に守らせる仕組み。AI 向けの要約は リポジトリ直下の CLAUDE.md。

1. ハーネスの構成

層ファイル役割
ルール（常時読込）CLAUDE.mdAI が毎回従う絶対ルール・アーキテクチャ制約
検査スクリプトscripts/check-docs.mjs文書の整合性（ナビ・リンク・要件ID参照・決定参照・changelog更新）
scripts/trace.mjsコード/テストの @req タグと要件IDの対応。--report で必須要件の実装・テスト状況
scripts/verify.mjs品質ゲート。上記 + typecheck / lint / test（package.json に定義があれば）
自動フック（Claude Code）.claude/settings.json編集直後に軽量チェック、終了時に品質ゲート。失敗すると AI が修正を続ける
Git フック.githooks/pre-commitコミット前に品質ゲート（人間・AI 共通）
作業手順（スキル）.claude/skills/*/spec-change /implement-feature /doc-audit /tech-spike
レビュア（サブエージェント）.claude/agents/*doc-auditor（文書の意味的整合）、arch-reviewer（レイヤ・セキュリティ違反）

2. ドキュメント整合ルール

  • 仕様の正は docs/*.html。コードより文書が先。
  • 仕様に影響する変更は、関連する全文書を同じ作業で更新し、変更履歴に追記する（仕様文書の変更だけをコミットしようとすると pre-commit が拒否する）。
  • 要件IDは再利用しない（削除は欠番）。他文書の ID 参照は存在するものだけ（機械検査）。
  • 決定事項は 未決事項の回答欄に「決定:」で記録。未決の★に依存する実装は、先にユーザーへ確認。
  • 新規ページを追加したら全ページのナビに追加（機械検査）。
  • コードと文書が食い違ったら、AI は黙って片方に合わせず報告する。

3. 設計ルール

src/
├─ domain/    純TS。日付計算・依存検証・diffSchedule・マイグレーション・コマンド適用
├─ shared/    IPC型・zodスキーマ
├─ main/      Electron main: Git(dugite)・FS・IPCハンドラ
├─ preload/   contextBridge
└─ renderer/  React UI: components/ interaction/ store/
tests/        src と同じ構成の単体テスト、tests/e2e は Playwright
spike/        技術検証の使い捨てコード（本体に混ぜない）
ルール内容
依存方向domain ← shared ← main / renderer。domain は electron・node:*・react・DOM を import しない。renderer は main を import しない
強制スキャフォールド時に ESLint の import 制限（レイヤ境界）を設定し、lint を品質ゲートに含める
Electron セキュリティcontextIsolation 有効、nodeIntegration 無効、IPC は型付き＋入力検証、FS/Git は main のみ
依存追加理由を architecture.html に記録。d3 のモジュール追加は自由
設計変更方針を変える場合は先に文書（architecture.html）を更新・合意してから実装

4. 実装ルール

  • TypeScript strict。any は理由コメントなしで使わない。
  • 日付は YYYY-MM-DD 文字列。Date・タイムゾーン依存を持ち込まない。
  • 状態変更は全てコマンド経由（UI・キーボード・将来の自動化が同じ経路）。ドラッグ中は ref + rAF、確定時に1コマンド（= Undo 1単位）。
  • イベントはルートで委譲、Pointer Events + setPointerCapture（architecture 参照）。
  • JSON 出力規則（キー昇順・インデント2・LF・IDキー）を守る。形式変更は schemaVersion とマイグレーションを伴う。
  • 実装には @req F-xxx タグを付ける（存在しない ID は機械検査で error）。
  • ライブラリの機能が足りないときは、まず標準機能・既存コードを探し、不要な抽象化をしない。

5. テストルール

層ツール方針
domain 単体Vitestテスト先行。正常系・境界（月跨ぎ・年跨ぎ・閏年・月曜起点）・不正入力。カバレッジ目標 90%+
diffSchedule / マイグレーションVitest変更種類ごとの入出力例（スナップショットでなく明示的な期待値）。旧スキーマ→新スキーマの往復
Git 連携Vitest + 一時リポジトリ実際の git を使い、競合・オフライン・認証失敗を再現
性能ベンチ（500×50×8年のデータ生成）描画・イベントに関わる変更で確認。基準は NF-001
UI 主要フローPlaywright for Electron表示→ドラッグ編集→保存→共有→競合解決 など主要経路のみ
  • バグ修正は再現テストを先に書く。
  • テストには @req タグを付け、node scripts/trace.mjs --report で必須(M)要件のテスト有無を確認する。
  • テストを通すためにテストを弱めない。仕様が誤りなら文書から直す。

6. 完了の定義 (DoD)

  1. 要件ID が requirements.html にあり、実装とテストに @req タグがある
  2. 関連文書が更新済みで、changelog に記録されている
  3. node scripts/verify.mjs が全て通る
  4. レイヤ違反・セキュリティ違反がない（必要に応じ arch-reviewer）
  5. 性能要件に関わる変更は計測済み

7. コミット・ブランチ

  • コミットはユーザーの依頼があったときだけ。push も同様。
  • メッセージ: type(scope): 概要 [F-201]（feat/fix/docs/test/refactor/chore）。1コミット1論点。
  • 禁止: force push、reset --hard、--no-verify、履歴書き換え。
  • pre-commit 有効化（クローン後に1回）: git config core.hooksPath .githooks
