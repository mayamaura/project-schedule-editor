未決事項・追加で定義すべき要件

設計への影響が大きい順。★は「実装前に必ず決めたい」項目。回答は各行の右欄に追記してください。

A. 設計を左右する重要事項

#質問選択肢/推奨回答
★A1依存関係の端点は何かプロジェクト間のみ / イベント・マイルストーン間（推奨: 後者。前者も内包できる）
★A2日程の自動連動（スケジューリング）をするか。先行を動かすと後続が自動で動くかしない・違反を警告のみ（推奨・MVP）/ 手動で「連動移動」/ 常時自動
★A3親の期間は子から自動集計か、独立した値か自動集計表示（推奨）/ 独立入力 / 両方
★A4同時編集者の人数と運用1人 / 数人 / 十数人以上。→ 運用モデルの選択に直結
★A5リモートリポジトリの種類GitHub / GitLab / Azure DevOps / 社内サーバ / 共有フォルダ（bare repo）/ ローカルのみ
★A6想定規模プロジェクト数・イベント数・期間（例: 200行/3,000イベント/5年）→ 描画方式の判断材料
★A7対象OSWindows のみ / Windows+macOS(+Linux)
A8プロジェクトの親子は単一親（木）か、複数親（DAG）か単一親（推奨）
A9日付の粒度日単位のみ（推奨）/ 時刻あり / 半日
A101行内でイベントが重なる場合の表示行を自動で縦に展開（推奨）/ 重ね表示 / 禁止

C. 決めておくと進行が楽になること

  • MVP の範囲: 「表示+編集+保存/共有」まで、を最初のリリースとする案（比較・案機能・出力は次段階）。
  • サンプルデータ: 実際の（匿名化した）案件データを数十件提供してもらえると、UI/性能検証が現実的になる。
  • 受け入れ基準: 「Git 未経験者が説明なしに保存→共有→競合解決を完遂できる」など、検証可能な基準。
  • 参考にしたい既存ツール: 好きな点・嫌いな点（Excel、MS Project、Notion タイムライン等）。

D. 推奨する進め方

  1. 本ドキュメントに追記 → A の★項目を確定
  2. 技術スパイク（描画性能 / dugite 認証 / 競合解決の最小プロトタイプ）
  3. データモデル確定 → ドメイン層＋テスト実装
  4. UI（表示 → 編集 → 依存 → ビュー）→ Git UI の順に実装
その他、思いついた要件を自由に追記。
