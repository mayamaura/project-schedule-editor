ロードマップ（MVP と設計・実装・テスト）

文書ステータス: v0.2（2026-11-07）。MVP の範囲・リリース順・前提は 未決事項 K で確定済み（変更は /spec-change）。全ての要件は、この文書のどこかのフェーズに割り当てる（check-docs が機械検査する。要件を追加したら、ここも更新する）。

1. 進め方の原則

  • 縦切り（スライス）で進める。各フェーズを、動いて見せられる小さな単位（約1週間）に分け、毎回「設計 → テスト先行 → 実装 → 検証 → 文書の整合 → デモ」を回す。
  • リスクの高いものを先に。EMU 認証、実機での描画性能、Git 初心者向け UI の使いやすさは、早い段階で実環境・実利用者で確かめる。
  • 土台から積む。ドメイン層（純 TypeScript）→ 表示（Canvas）→ 編集 → Git → 配布。下の層が固まるまで、上の層の見た目は作り込まない。
  • 品質ゲートを毎回通す。scripts/verify.mjs（文書整合・要件ID追跡・ライセンス・型・lint・テスト）が通らないものは「完了」としない。ゲートはフェーズごとに強化する（6.2）。
  • 仕様は先に文書、実装は後。フェーズの冒頭で、そのフェーズの詳細設計を文書に反映する（/spec-change）。フェーズの終わりに /doc-audit で文書とコードを突き合わせる。
  • AI（Claude Code）との協働の標準サイクル: /implement-feature（要件ID単位）→ arch-reviewer（レイヤ・セキュリティ違反の確認）→ コミット。
期間は概算（開発者1人が AI と協働し、ほぼ専任で進める前提。不確実性は ±50%）。確度が低いため、Phase 2 の完了時に実績で見直す。体制・稼働の前提は確定（K4: 開発者1人が AI と協働・ほぼ専任。パイロットは3名・2週間）。

3. MVP の定義（確定）

MVP = 「日程を1人で編集でき、Git（作業版 → 正式版）で複数人と共有できる」最小のアプリ。Phase 0〜4 の完了（2026-11-08 の変更: 旧 Phase 5 の配布は MVP の後、リリース R6 として最後に行う。MVP は開発版で動作確認する）。
